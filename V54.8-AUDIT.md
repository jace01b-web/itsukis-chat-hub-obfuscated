# ICH v54.8 — technical audit report

Built from the v54.7 source ZIP. Existing architecture, Firebase integration, Discord-inspired
shell, account system, profiles, moderation, servers and chat are preserved; nothing was
rewritten from scratch and no feature was removed.

**Read first:** [Deployment](#deployment) — one of the three rules additions breaks a working
feature if it is not published.

---

## 1. Former-owner security issue

### 1.1 Exact root cause

**It was not a hole in the Firebase rules.** The rules were correct throughout, and the
regression suite added in this release proves it against a real rules evaluator.

ICH grants site ownership from **two** database nodes:

| node | effect | who can read it |
|---|---|---|
| `owners/$id` | full owner powers, **and** the Owner tag | every signed-in account |
| `secretowner/$id` | full owner powers, **no** tag | **nobody** — `".read": false`, except your own entry |

All four authorization layers honour both, correctly and consistently:

- `isOwner()` in `js/moderation/roles.js` — `OWNERS_CACHE[id] === 1 || SECRET_OWNER_ID === id`
- the database rules — every privileged write tests `owners/<id> === 1 || secretowner/<id> === 1`
- `roleOf()` in `api/_lib.js` — reads `owners/`, `secretowner/`, `admin/`
- the announcements composer lock in `js/chat/chat-view.js`

So **removing an account from `owners/` in the Firebase console removed its tag and nothing
else.** If that account also held `secretowner/$id === 1`, it kept every power it had ever had —
announcements included — while looking like an ordinary member everywhere in the interface.

The reason it went unnoticed for a release is the second half of the defect: **no screen in ICH
could show that the grant was still there.** `secretowner` is unreadable from the browser by
design, the Owner Control Center deliberately does not manage owner grants
("Those carry real power and are changed from the Firebase console"), and nothing anywhere could
enumerate the node. The grant was not merely un-revoked; it was **invisible and untrackable**,
which is exactly the condition section 1.3 of the brief warned about.

### 1.2 Exact affected permission paths

Everything gated on `owners/ || secretowner/`, which is every site-level power:

- `liveAnnouncement` (the broadcast banner)
- `messages/announcements/*` (the Announcements channel — create, edit, delete)
- `appVersion/current`, `modSettings/*`, `reconnectRequest`, `banned/*`, renaming any account
- every `api/` endpoint whose `roleOf()` result is checked (`customrole`, `ipban`, `totmilestone`, …)

### 1.3 Was `secretowner` involved? Was ID mapping involved?

- **`secretowner`: yes.** It is the whole root cause.
- **ID mapping: no.** `uidToId/$uid` and `idToUid/$id` are both write-once in the rules
  (`!data.exists()`), the API never trusts a client-supplied numeric id, and the announcement
  rule binds `idToUid/<senderId> === auth.uid` so a forged `senderId` is refused. All of this was
  already correct and is now covered by tests. The audit endpoint still **checks** mappings for
  integrity, because "does this account resolve to somebody else's id" was a question the brief
  asked and nothing could previously answer.

### 1.4 What was changed

**`api/ownership.js` (new).** The tool that did not exist. Owner-authenticated, server-resolved:

| action | does |
|---|---|
| `audit` | lists every account in `owners/`, `secretowner/`, `admin/`, `mods/` with its uid, username, ban state and **problems**: `orphan-secret-owner`, `mapping-mismatch`, `no-idToUid-mapping`, `no-user-record`, `banned-but-owner` |
| `check` | the same for one id — "why does this account still have powers?" |
| `revoke` | removes the grants in **one multi-path write**, appends `ownerLog/`, bumps `authEpoch/$id` |

It **cannot grant.** Granting stays a Firebase-console action, which is the existing design. The
asymmetry is deliberate: the worst a stolen owner token can do here is take powers away, which is
recoverable from the console, whereas an escalation path would not be. Two rails: the **last
remaining owner cannot be revoked**, and revoking yourself needs `confirmSelf: true`.

**Owner Control Center → Ownership (new section, second in the list).** Every grant, with the
secret ones in the most prominent colour, each problem written out in a sentence that says what
to do, and a one-click *Revoke secret ownership* on any orphan.

**`api/_lib.js` — one canonical server-side model.** Eight endpoints each repeated
`verifyToken → uidToId → roleOf`, and had drifted (some checked `banned/`, some did not).
`resolveCaller(body)` and `requireOwner(req,res,body)` are now the only way an endpoint learns who
is calling. **Nothing in the request body contributes to identity** — there is deliberately no
parameter by which a caller can name itself.

**`js/moderation/roles.js` — one canonical client-side resolver.** `isOwner`, `isShownOwner` and
`ownersKnown` keep their exact signatures and answers (the whole app calls them) and now delegate
to one `AUTHZ` object that can also report *which* grant applied, plus `AUTHZ.assertOwner()`,
which refuses while the grant tables are still loading.

**Stale session state.** `stopAll()` cleared listeners and `C.priv` and left the rest of `C`
intact, so signing into another account in the same tab showed the **previous** account's
profile, perks, roles, friends and unread state until each listener's first snapshot landed.
`resetAccountCaches()` now clears all of it, and closes the settings panel and any open profile
card, both of which belonged to the previous account.

### 1.5 How former permissions are revoked, and how current owners stay authorized

Revocation is a single multi-path write, so there is no instant in which `owners/` is gone and
`secretowner/` is not — the exact state the bug was living in. `owners/` and `secretowner/$myId`
are both watched live, so the permission disappears in every open tab without a reload.
`authEpoch/$id` (new) then handles the rest of the cleanup: the client refreshes its Firebase ID
token and closes any owner-only screen still open, instead of leaving a panel whose every button
will now bounce off the rules.

A **legitimate** owner, shown or secret, is untouched: no rule was tightened, and tests 1 and 2
below assert both still work.

### 1.6 Announcements specifically

Both paths were audited and are covered by tests: `liveAnnouncement` and
`messages/announcements/*`. The announcement rule tests `owners || secretowner` on the message's
`senderId`, **and** binds that `senderId` to `auth.uid` through `idToUid` — so a forged sender is
refused, and no server-level permission can reach it (the `$key === 'announcements'` branch is
checked before any `channelServer` logic). The frontend composer lock uses the same resolver.

### 1.7 Required regression tests — `test/security/former-owner.js`

**56 checks, all passing**, executed through **targaryen** (a real implementation of the Realtime
Database rules language) against the rules file that actually gets published.

| Scenario | Expected | Result |
|---|---|---|
| Current legitimate owner | Allowed | ✅ |
| Current legitimate secret owner | Allowed | ✅ |
| Former owner, both grants cleared | Denied | ✅ |
| Former secret owner after revocation | Denied | ✅ |
| Ordinary member | Denied | ✅ |
| Server owner without site ownership | Denied | ✅ |
| User changing their display name | No permission change | ✅ |
| User changing their username | No permission change | ✅ |
| User supplying another numeric user ID | Denied | ✅ |
| User using a stale browser cache | Denied | ✅ |
| User writing directly to Firebase | Denied | ✅ |
| Privileged API with a forged identity | Denied (no identity field exists) | ✅ |

Section 3 of that suite **reproduces the bug deliberately**: an account with `owners/` deleted and
`secretowner/` left behind, asserted as **allowed**, because with the grant still present it *is*
an owner by the only definition the rules have. No rules change can distinguish it from a
legitimate secret owner — the two are identical at the database level. That is precisely why the
fix is a tool that can see and clear the grant rather than a rules edit, and the case is asserted
rather than skipped so that nobody ever "fixes" it by weakening the secret-owner feature.

### 1.8 What must be published

See [Deployment](#deployment). The three additions are additive; **no existing rule was relaxed
and no read was widened.**

## 2. Performance

### 2.1 Actual bottlenecks discovered

Measured, not assumed — `js/core/perf.js` (new) counts the work, `test/run-perf.js` (new) drives
a 600-account / 300-message / 40-DM / 4-server load and reads the counters out.

**A. `DB.onChange` carried no information about what had changed.**
Coalescing to one flush per frame was already in place and already right. What was missing is
*what moved*. Every subscriber got the same contentless "something happened", so every subscriber
did its maximum work — and `js/chat/live-sync.js` ended with an unconditional
`renderChatLight() → renderChat()`, a full rebuild of the sidebar, the message list and the whole
shell. With ~450 live listeners, somebody going idle, somebody editing an avatar, a reaction on an
old message in another channel and a presence heartbeat all rebuilt the interface.

**B. `checkPingNotifications()` walked every cached message on every flush.**
Joined channels plus DMs, each array walked end to end — ~1,500 messages per call on the test
load, on every database event, however unrelated. `_notifiedMsgIds` was an unbounded `Set` that
nothing ever removed from: a slow leak proportional to how long the tab stayed open.

**C. The member sort built a collator per comparison.**
`nameOf(a).toLowerCase().localeCompare(nameOf(b).toLowerCase())` — `localeCompare` constructs a
collator on every call (~5,000 per render at 600 members), and `nameOf` was called twice per
comparison (~10,000 `peekUser` + `dispName` calls) to produce at most 600 distinct answers.

**D. The member list rewrote its DOM even when the markup was identical.**
`innerHTML =` on 1,200 rows costs a parse, a style recalc and a layout — and drops scroll position
and hover — even when the output is byte-for-byte what is already on screen.

### 2.2 Changes implemented

- **Topics.** `emit(topic)` tags each event; `listen()` derives the topic from the path it
  watches, so no call site can forget. Subscribers get `topics.has(…)` / `topics.only(…)`.
  An untagged emit still means "assume everything" — the pessimistic direction.
- **A status change is a presence event.** `_userRenderSig()` compares the fields of a user
  record that are drawn *outside* the member list. Status/custom-status only → `presence`;
  a name, avatar or bubble colour → `users`, because those appear on every message that person
  has sent. A profile arriving for the first time is also `presence` unless that person actually
  has a message in the open conversation or a DM row.
- **The cheap path.** `refreshPresenceLight()` updates the online pill, the sidebar dots (a class
  toggle per row) and the member list — built from the renderers that already exist, so there is
  no second implementation to drift.
- **The notification scan is incremental.** A per-conversation high-water mark on `at`; the scan
  walks backwards from the newest and stops at the mark. `_notifiedMsgIds` is a FIFO capped at
  3,000, and both are cleared per account.
- **One `Intl.Collator`** for the session, and names resolved once into a map before sorting.
- **The member list skips its DOM write** when the generated markup is unchanged.
- **Listener bookkeeping** is now observable: `DB.listenerCount()` / `DB.listenerBreakdown()`.

### 2.3 Before / after — measured

Same machine, same harness, same load (600 accounts, 300 messages in the open channel, 40 DMs ×
30, 4 servers × 6 channels × 20). Absolute milliseconds are a **floor**, because Firebase itself is
the fake in-memory implementation; the **ratios** are properties of the client logic and transfer.

| Scenario | Metric | Before | After |
|---|---|---|---|
| **60 presence changes** | full chat rebuilds | **60** | **0** |
| | time in `renderChat` | **659 ms** | **0 ms** |
| | member-list rebuilds | 60 (378 ms) | 60 (varies; sort is cheaper) |
| | wall clock | 2,686 ms | 2,298–2,983 ms |
| **40 profile changes** | full chat rebuilds | **24** | **0** |
| | time in `renderChat` | **243 ms** | **0 ms** |
| **30 messages arriving** | full chat rebuilds | 31 | 31 *(correct — the messages must render)* |
| | messages walked by the scan | **45,525** | **30** (**99.9 % avoided**) |
| **12 channel switches** | per-rebuild average | 33.3 ms | 26.8–36.7 ms |
| **20 channel switches** | listener drift | — | **0** |

The 45,525 → 30 figure is measured **in the same run**: `pingMsgsInScope` counts what the old
whole-array walk would have examined while `pingMsgsScanned` counts what the incremental walk
actually examined, so it is a direct comparison rather than a remembered number.

### 2.4 Remaining limitations — stated plainly

- **A message arriving still triggers a full `renderChat`.** Incremental message insertion and
  virtualization are listed in the brief (2.2) and are **not** implemented. At ~27 ms per rebuild
  on a 300-message channel this is acceptable, and it is the largest remaining win.
- **The member list still sorts and builds its string on every presence tick**; only the DOM write
  is skipped. The sort is much cheaper now, but it is not free.
- **Absolute timings come from a fake Firebase.** Network latency and the real SDK's own work are
  absent.
- **Long tasks**: 36 observed over the full run. Not zero.
- Scroll-position guards (2.3) are addressed by CSS `overflow-anchor` only; the pagination
  scroll-restore logic was not rewritten.

## 3. Presence, status and DND

### 3.1 How status resolution works

`DB.statusOf(id)` is the single canonical resolver. Two facts decide a status and they live in
different places — `users/$id/style/status` (what they *chose*) and `onlineUsers/$id` (whether
they are *connected*). Before v54.8 this function read only the first, so an account that had
never touched the status picker reported **Online forever**; components that checked
`onlineUsers` themselves got it right and components that asked this got it wrong. That is
exactly the "online in one location, offline in another" of section 5.1. Both facts are folded in
now. `chosenStatusOf(id)` returns the raw choice, for the picker and for auto-idle.
`js/social/profile-card.js` had its own three-step copy; it now delegates.

### 3.2 How DND suppresses notifications

**The policy was never wrong. It simply had no callers.** `Prefs.quietHours()` already returned
true for a Do Not Disturb status as well as for a scheduled window, and `Notifier` already
consulted it — but in v54.7 `Notifier.message()` had **zero callers** outside the settings test
button. The two things that actually notified people went around it:

| file | what it did | consulted |
|---|---|---|
| `js/chat/messages.js` | `if (ME.settings.pings.sound) beep()` | one account switch |
| `js/chat/pings.js` | `new Notification(name, {…})` | one account switch |
| `js/moderation/bans.js` | `beep()` on an owner announcement | nothing |
| friend requests | *nothing at all* — `Notifier.friendRequest()` had no callers | — |

All four now route through `Notifier.message()`. `Notifier.suppressed()` returns a **reason**
(`dnd`, `quiet-hours`, `muted`, `mentions-only`, `dm-off`, `desktop-off`, `sound-off`) rather than
a boolean, which is what the tests and the diagnostics assert on.

### 3.3 What happens to unread messages

Nothing. `Notifier` plays a sound and raises a notification; it does not decide whether a message
is delivered, stored, shown or counted. Those live elsewhere, which makes "continue receiving
messages, preserve unread counts" true by construction rather than by remembering to special-case
it. An owner announcement's **banner still appears** under DND — DND hides alerts, not content.
`test/run-dnd.js` asserts all of this directly: messages sent during DND are in the database,
unread badges appear, and the messages render when the conversation is opened.

### 3.4 Custom status and automatic idle

- **Terms** (section 5.3): Never / 30 minutes / 1 hour / 4 hours / Today, stored as
  `style/customStatusUntil`, written with the text in **one multi-path update** so a term can
  never be orphaned from its text. An expired status stops being **displayed** by every client
  immediately (`DB.customStatusOf` filters it) and is **deleted** by its owner's next sweep —
  there is no Cloud Function in this project, and the display rule is what makes expiry correct
  for everybody regardless.
- **Automatic idle** (`js/core/idle.js`, new): Online → Idle after 10 minutes of inactivity, back
  on activity. It only ever touches a status that is exactly `online` (to leave) or an `idle`
  **it set itself** (to return) — DND and Invisible are never changed. Decisions are made from a
  wall-clock comparison re-evaluated each tick, **not** by counting ticks, because browsers
  throttle background timers; a hidden tab therefore concludes late rather than wrongly, and
  becoming visible counts as activity. Activity is shared between tabs through `localStorage`.
  One interval, one timestamp per second, a floor under its own writes.

### 3.5 Tests — `test/run-dnd.js`

**33 checks, all passing.** `window.Notification` and the audio constructors are replaced with
counting stubs before the app starts, so "did this make a noise" is a number. Covered: mention,
DM, @everyone, owner announcement and friend request under DND; delivery and unread counts
surviving DND; scheduled quiet hours; muted channel; desktop-off; sound-off; and all four paths
together producing **zero** alerts under DND.

## 4. Context menus

### 4.1 Which systems were consolidated

There were two implementations: `openCtx` (`js/discord/ui.js`, the `.dctx` menu used by servers,
categories, channels, members, messages and profiles) and a separate `.ctx-menu` in
`js/ui/context-menu.js` for the generic page menu. Different markup, different positioning,
different closing rules, no shared keyboard model — and because the generic one listened on the
document, **right-clicking a channel opened both, stacked on the same pixel**. That had been
papered over with a `document.querySelector('.dctx')` probe and a comment explaining why the
obvious test (`defaultPrevented`) could not work.

`js/ui/context-menu.js` now **describes its items and hands them to `openCtx`**. One menu element,
one positioner, one set of closing rules, one keyboard model. The stacking bug cannot return
because there is only ever one menu to open.

### 4.2 What `openCtx` gained

Submenus (as their own viewport-positioned element, so a long submenu is not clipped by its
parent); full keyboard control — arrows, Home/End, Enter/Space, Escape, Left/Right for submenus,
and type-ahead; focus moved into the menu and **returned** on close, falling back to the nearest
surviving ancestor when the anchor has been re-rendered away; `role="menu"` / `role="menuitem"` /
`aria-haspopup` / `aria-expanded` / `aria-disabled` instead of anonymous divs (section 12);
viewport **flipping** rather than clamping; internal scrolling for menus taller than the screen;
and `ctxLongPress()` for touch, which cancels on movement so it never interferes with scrolling
and swallows the click that would otherwise follow.

### 4.3 New contextual actions

**Message menu** (section 8.2), now complete: Reply, Add Reaction, Edit (own), Delete (own or
authorized), Pin/Unpin, Save, a **Copy** submenu (Text, Message ID, Message Link, User ID,
Username), View Profile, Ignore, Report.
**Page menu**: Settings, Profile Settings, a **Set Status** submenu, Fullscreen, Reload, Home,
Sign Out.

### 4.4 How permission checks work

Only valid actions are **shown**, and that is a presentation decision rather than the enforcement.
Edit asks the same question `DB.editMessage` and the rules ask; Delete uses the same `outranks()`
ladder and server `manageMsg` test the hover bar uses; Pin asks `DPins.canPin`. If every check
were deleted, the extra items would simply be refused by the database. Report copies the details
for a moderator rather than pretending to file something — there is no reporting backend in this
project, and an honest half-feature beats a convincing dead one.

### 4.5 What stays native — and why

Text fields, links, images, media and any active text selection keep the **browser's** menu.
Replacing it there costs spellcheck, Paste, Save image as, Open in new tab and Search for
selection, and ICH has nothing better to offer in their place.

### 4.6 Tests — `test/run-ctxmenu.js`

**50 checks, all passing**: exactly one menu per right-click on a channel, a member, a message and
the page background; the message menu's action set on own and others' messages; submenu open /
ARIA / parent staying open; arrows, Home, End, Enter, Escape, Left/Right; focus in and out; both
corner cases of viewport flipping; and native-menu preservation on inputs, textareas, links,
images, contenteditable and a selection.

## 5. Profiles and settings

**Files changed:** `js/social/profile-card.js`, `js/social/profile-data.js`,
`js/settings/settings-page.js`, `js/settings/settings-plus.js`, `js/ui/discord-shell.js`,
`js/core/database.js`.

### Bugs fixed

- **Stale profiles.** An open card was repainted only by the things that *knew* about it (the
  async badge/connection fetches, and the settings panes after an explicit save). A profile
  edited anywhere else — on another device, by a moderator, through any path that forgot to call
  `repaintAll` — sat there showing the old avatar, name and status until it was closed and
  reopened. The card now follows the database, filtered by topic so a message arriving does not
  repaint a profile. (Section 4.4: "stale information", "profile not refreshing after an edit".)
- **Cross-account profile bleed.** Every profile module cached per-account data — including
  **private notes**, mutual-friend lists, badge/boost counts and connections — and none could be
  told "this is a different person now". `profileCacheReset()` clears all of it on an auth change
  and closes any open card. The notes make this a privacy problem, not a cosmetic one.
- **Settings showing the previous account.** The settings panel is built from one account's
  settings object, read when it opened. It now closes on an account switch, through the path that
  also drops the music listeners, the ban-list subscription and the mute timer.
- **A listener leak:** every profile opened left a `keydown` listener on the document for the life
  of the page. `PCard.closeAll()` tears a card down properly.
- **Racing saves** on the custom status (blur *and* Enter both firing) are serialised.
- **Status disagreeing with itself** — see §3.1.

### Settings reorganisation (section 7)

The navigation was already Discord-shaped (User Settings / Billing / App Settings / ICH / Staff
with a sidebar and separate panes), so it was kept. What was missing is the category the brief
names and the app did not have: **Activity & Presence**, added next to Notifications. It holds the
status picker, the custom status with its term, a live read-out of the automatic-idle state, the
current quiet-hours state, and the activity-sharing toggle. The problem it solves is real: status,
automatic idle and the custom status were reachable only from a small popout above the account
panel, and the two halves of Do Not Disturb — the **status** and the scheduled **window** — lived
in different places with nothing saying they were the same feature.

### Still outstanding

The deeper profile work in sections 4.2–4.5 — the banner/avatar redesign, tabs in the full
profile, and a structured editor with preview and an unsaved-changes indicator — is **not done**.
See §8.

## 6. UI, density and responsive

Changes were made from screenshots at 1500×900 and 390×844, not from assumption. All v54.8 CSS is
in **one** new layer, `css/31-v548.css`, loaded last so it can correct the layers above it without
`!important`, using existing design tokens. Both CSS lists (`index.html` and `js/manifest.js`) are
synchronized and verified.

- **The seam in the chat column.** `.main` set no background, so the message scroller showed the
  *app* background (`#1e1f22`) while the topbar and composer above and below were `#313338` — a
  dark band with two lighter bars clamped onto it. The column is now one colour throughout, as
  Discord's is. Scoped to the Discord look, where the user-chosen chat background is deliberately
  hidden, so nothing is covered up.
- **Messages sit at the bottom.** A short conversation was pinned to the top of a 742 px scroller
  with hundreds of pixels of nothing above the composer. Fixed with `margin-top:auto` on the first
  child rather than `justify-content:flex-end`, which makes overflowing content unreachable above
  the scroll origin in some engines and would have hidden the oldest messages.
- **Mobile channel name clipped mid-word** ("# genera"). Two causes: the topbar's left group had no
  `min-width:0`, so it could not shrink below its content; and the icon row was **258 px of a
  390 px screen**. Below 480 px the three buttons with another route on a phone step aside
  (Settings → account-panel gear and the page menu; Saved → the message menu; Rules → the channel
  list). Member list, Pins and Search stay. The name now fits in full.
- Touch targets raised to 40–44 px; horizontal page scroll prevented; `prefers-reduced-motion`
  honoured for menus; focus rings on menu items and selects.

**The Firebase Emulator could not be run and is reported as blocked, not as passed.** Its

only missing piece is the download. Rules validation was therefore done with **targaryen**, which
is a real implementation of the rules language — a different implementation from Google's, and
where the two ever disagree, Google's is right.

**One existing test was updated, not deleted:** `test/run-v54-7.js` asserted the Owner Control
Center's exact five sections. v54.8 adds a sixth (Ownership), so the expectation is updated — it
still pins the exact set **and order**, so a section vanishing or being reordered still fails.

Three new npm scripts: `test:owner`, `test:dnd`, `test:ctxmenu`, `test:perf`. The new browser
suites are wired into `npm run test:browser`.

## 8. What was NOT done

Stated plainly rather than implied by omission.

- **Profile redesign (brief §4.2, §4.3, §4.5).** The popout and full profile keep their v54.7
  layout. The banner/avatar redesign, tabbed sections, and the structured editor with preview,
  validation and an unsaved-changes indicator are **not implemented**. The profile *bugs* in §4.4
  are fixed and the architecture was left consolidated rather than forked.
- **Incremental message rendering and virtualization (§2.2).** The largest remaining performance
  win, as above.
- **Member-list search and empty states (§9), Discover/Games/Moderation screen polish (§10).**
- **Accessibility (§12)** was improved for context menus and the new panes only; there was no
  app-wide audit.
- **The emulator rules run (§16.1)** — blocked, as above.
- Touch long-press is **exercised**, not proven: synthetic touch in a headless browser does not
  reproduce a real finger's timing, and the suite says so where it says so.

## Deployment

1. **Publish `firebase-rules.json`** — Firebase console → Realtime Database → Rules → Publish.
   (`firebase-rules.min.json` and `rules-copy.html` are the same document; all three are verified
   identical.) Three **additive** nodes; nothing was relaxed and no read was widened:
   - `ownerLog/` — owner-read, `".write": false` for every client
   - `authEpoch/$id` — readable by that account only, `".write": false`
   - `users/$id/style/customStatusUntil` — a number, ≤ 400 days ahead
   > **Without (3), setting a custom status is refused outright**, because the client writes the
   > text and the term in one multi-path update. This is the one change that breaks a working
