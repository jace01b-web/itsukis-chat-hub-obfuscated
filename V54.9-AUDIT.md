# ICH v54.9 — audit, fixes, interface work and what was actually tested

Built from the v54.8 tree. Version in `package.json` is now `54.9.0`.

This document answers section 11 of the brief. Where something was **not** done, or could not be
run, it says so plainly rather than leaving you to find out.

---

## 1. Bugs found

Each of the five bugs in section 2 of the brief was first **verified against the current code**
before anything was changed, as the brief asked. Three turned out to be real as described, one
was real but had a different root cause than the brief assumed, and one was partly already
fixed. Five further bugs were found during the audit that the brief did not name.

### The five named bugs

| # | Bug | Verdict after reading the code |
|---|---|---|
| 2A | Two parallel notification systems | **Confirmed.** `settings-page.js` wrote `pings.{desktop,sound,everyone}`; `settings-plus.js` wrote the scalars `desktopNotif` / `notifSound`; `pings.js` read only the `pings` map. Turning a toggle on in one screen did nothing in the other. |
| 2B | Wrong notification context when opening a DM | **Confirmed.** `messages.js` used `view.sid`, which still held the *previously* open server. |
| 2C | Per-server / per-channel controls unfinished | **Confirmed.** `NotifPrefs.setChannel()` had no call site anywhere, and the server context menu's "Notification Settings" entry just opened the global settings page. |
| 2D | Discover loading / error states | **Confirmed.** Listener errors were only `console.warn`'d, a 4-second timer flipped "loading" to "ready" regardless of outcome, and Retry set a flag, waited 600 ms and claimed success without re-reading anything. A refused read rendered as *"No servers are listed yet"* — an error presented as a fact. |
| 2E | Notification scanning reliability | **Partly confirmed.** The scan was correct for the common case but used a timestamp-only cursor, so a second message with an identical timestamp, or one inserted below the cursor by clock skew, was silently never notified. |

### Five more found during the audit

| # | Bug | Why it mattered |
|---|---|---|
| A1 | **`DB.updateSettings` was destructive.** It merged from the *public* settings node — which had been emptied in an earlier release — and then `set()` the private blob. | Any partial settings write wiped every other private preference. Found because the 2A migration reduced a test account's settings to two keys. This is the most serious bug in the release. |
| A2 | **Server channels had no preview listeners.** `C.messages['ch_*']` was never populated. | Two visible symptoms with one cause: unread badges on server channels always read 0, and an `@mention` in a server channel **never notified you at all**. |
| A3 | **`defaultSettings()` synthesises `pings`,** so the legacy-value fallback fired for every account including brand-new ones. | Would have given new accounts legacy defaults instead of the real ones. Fixed by reading the raw stored node (`DB.rawSetting`) rather than the merged one. |
| A4 | **`NotifPrefs.effective()` counted `notifDM` twice** at the account level. | A muted DM could still notify. |
| A5 | **`Perf.msgRows` was declared and never incremented.** | A counter that always reads 0 is worse than no counter — the next person measuring render cost reads "0 rows written" and concludes the message list is free. |

### Two reported defects that turned out **not** to be defects

Both came out of screenshots and both were disproved by measuring the live DOM. They are
recorded here, and asserted in `test/run-ui549.js`, so nobody "fixes" them again:

- **The MVP member row looked like it overflowed the member panel.** Measured: nothing inside
  `#dlMembers` extends past its right edge at any width. The apparent block is headless Chromium
  painting a `-webkit-background-clip:text` gradient into a screenshot.
- **The "Today" divider looked clipped by the channel header.** Measured: `.date-sep` top 39,
  `#messages` top 48, `scrollTop` 25 — it is simply scrolled partly out of view in a
  bottom-anchored list, which is correct. A speculative CSS rule written against this
  misreading was removed again rather than shipped.

## 2. Bugs fixed

All ten real bugs above are fixed. The notable ones:

**2A — one canonical notification system.** `js/core/prefs.js` is now the single source of truth.
The scalars (`desktopNotif`, `notifSound`, `notifEveryone`) are canonical; a one-time migration
reads any legacy `pings` map and carries the user's actual choices across. Nothing is silently
reset — if the migration write fails, the marker is left unset so it retries next session, and
until then a legacy value is still honoured as a fallback. Desktop and sound are fully
independent: **a sound plays without ever requesting notification permission**, and turning
desktop notifications on when permission is denied reverts the toggle and says why instead of
leaving a switch that looks on and does nothing. `@everyone` still works.

**2B** — `messages.js` now resolves the server from the channel with `DModel.serverOfChannel(key)`
rather than trusting `view.sid`.

**2C** — a single shared `notifMenuItems(scope,id,sid)` builder in `js/discord/ui.js` now provides
All Messages / Only @mentions / Nothing / Reset to Default on channels, servers **and** DMs, with
the hierarchy channel → server → server default → account. Each entry shows whether the current
value is *set* or *inherited*; Reset is disabled when there is nothing to reset.

**2D** — Discover now has four genuinely distinct states: loading (skeletons, `role="status"`),
ready, true-empty, and error. Errors carry the real cause (`PERMISSION_DENIED` is named as such).
Retry actually re-attaches the listener. A mid-session failure keeps the list on screen behind a
"this may be out of date" banner rather than blanking it. Search text, focus and caret survive a
repaint.

**2E** — the cursor is now a deterministic `(timestamp, message-id)` comparison, so equal
timestamps and clock skew are both handled. The first attempt at this used a 120-second
look-back window and **caused a measurable performance regression** (10,217 messages scanned
where the budget was ~120). It was replaced with cache-shape detection. Final measurement:
**120 messages scanned against 59,925 the old algorithm would have walked — 99.8 % avoided**,
with every tie and skew case still passing.

**A1** — a new `DB.setSettingKeys(id,patch)` does an atomic multi-path update against the private
settings node. `updateSettings` was hardened to merge onto *effective* settings.

**A2** — `DB.syncChannelPreviews(keys)` keeps bounded preview listeners (cap 120, preferring
channels you have actually read) for server channels, driven from the model's `emitSoon()`.

## 3. Interface work

The brief's priority was *"less of a generic chat-bubble appearance and more of Discord's flat,
grouped message-row appearance"*. Everything below was done against screenshots at the widths in
section 4 and then **verified by reading computed styles and geometry out of the live page**,
because a screenshot cannot tell you whether a timestamp is 11 px.

- **Timestamps are secondary now.** They were a bare string inside `.meta` and inherited the
  username's size and weight, so `vlad 06:07 AM` read as two equally important things. They are
  wrapped in `.m-time`, set at 11 px / weight 400 in the muted token, with tabular numerals so
  the column does not jitter, and the full date on hover.
- **Your own messages look like everyone else's.** `.msg.me .meta` was reversed to read
  "time · name" — a leftover from when your messages were right-aligned bubbles. Every row is
  left-aligned in this look, so the reversal only made your own messages inconsistent. Name then
  time, for everybody. **No custom bubble colour or message styling was touched**; this is the
  order of two spans.
- **The channel header** separates the topic from the channel name with a hairline and sets it
  back in the muted token, ellipsised to one line so a long topic can never push the header
  buttons off the row. On phones the topic is hidden entirely — at 390 px it was being ellipsised
  down to `The ...`, which occupies space, tells you nothing and reads as a fault.
- **The composer names where you are** — `Message #general`, `Message @vlad` — instead of
  `Message... use @ to ping`. This matters most on mobile, where the channel list is behind a
  drawer. Every locked-state message (muted, announcements, TOS) is unchanged and still takes
  precedence. The placeholder is also ellipsised, which fixes it being clipped mid-wrap at 320 px.
- **The member list has a search field** (section 3F). It filters the id lists *before* grouping,
  so role groups, their order and their counts describe what is actually on screen. It has a real
  empty state, Escape clears it rather than closing the panel, and the caret and focus survive a
  presence repaint — without that, every presence tick would throw your caret to the end of the
  field mid-word.
- **The profile popout** is capped at viewport height and scrolls internally, so a member with
  many roles can still reach "View Full Profile" instead of having it fall off the bottom.
- **At 768 px and below the member list is an overlay**, not a column, so opening it never
  squeezes the message text.

All of this lives in **one** file, `css/32-v549.css`, following the project's existing
one-file-per-release convention (`29-v54`, `30-v547`, `31-v548`). Every value is an existing
design token. No new colours, gradients, glass effects or decorative elements were introduced,
and `css/31-v548.css` is untouched.

## 4. Performance

**The open question from section 6 — does a full `renderChat()` still run on message events? —
is answered, with a measurement rather than an argument.**

A burst of 40 incoming messages into an open channel was driven through the real listener path:

```
renderChat          : 86      (calls that entered the function)
renderChatSkipped   : 85      (returned early on the v54.8 topic guard)
msgRows             : 47      (message rows written to the DOM)
rows in the DOM     : 47
```

47 rows written for 47 messages — **each message drew exactly one row, and nothing was redrawn.**
If a full rebuild were running per message the row count would be in the thousands. The
incremental path is doing the work; the 86 entries are cheap guard checks, 85 of which return
immediately. **No virtualization was added**, because the measurement does not justify the risk
to scroll position, unread dividers, replies, reactions, editing and history loading. That is a
deliberate decision, not an oversight — see "Known issues" below.

The `msgRows` counter was fixed to make this measurable at all (bug A5).

### Tests that could NOT be run, and why

- **`npm run test:emulator` — BLOCKED.** The Firebase Emulator jar cannot be downloaded: the
  host is refused by the environment's egress proxy, and `gsutil` is refused for the same
  bucket. Java is installed; the blocker is purely network. **`targaryen` was used instead**, as
  a real rules evaluator, in `test/security/rules-audit.js` — 48 checks against the actual rules
  document. This is genuine rules validation, but it is not the emulator.
- **Live Firebase was never connected.** No claim in this document rests on it.
- **`tools/stamp-build.js` was not run.** It requires `BUILD_SECRET` from the environment, which
  is not present here and must not be invented. **The tree is therefore UNSTAMPED** — the dist
  test reports this explicitly. See deployment, step 3. No secret was read, printed or written
  into any file.

## 7. Deployment

1. **Publish the database rules.** Firebase console → Realtime Database → Rules → paste the
   contents of `firebase-rules.json` → Publish. v54.9 adds no new rules nodes beyond v54.8's
   three; if you already published v54.8's rules there is nothing new to publish. Rollback copy:
   `firebase-rules.v54-original.json`.
2. **Deploy the static files** (`index.html`, `js/`, `css/`, `api/`) as usual.
3. **Stamp the build** on a machine that has the secret:
   ```
   BUILD_SECRET=<the same value as in Vercel> node tools/stamp-build.js
   node build-single.js
   ```
   then set `MIN_BUILD` in Vercel to the label it prints. Do not edit the label by hand — the
   token is an HMAC of it and the API will reject a mismatched pair.
4. **Deploy `api/ownership.js`** if you have not already (it needs `FIREBASE_SA`). Everything
   else works without it; the Ownership section says so plainly when the endpoint is missing.

The old Nyckel and Discord webhook credentials noted in the project documentation were **not**
reintroduced anywhere, and should still be treated as compromised until their owners rotate them.

## 8. Known issues and deliberate omissions

Stated plainly, because the brief asked for them rather than for a clean-looking list.

1. **Message virtualization was not implemented.** Measured above: rendering is already
   incremental and draws one row per message. Virtualizing would put scroll restoration, the
   unread divider, reply jumps, reactions, inline editing, pinning and history loading at risk
   for no measured gain. If a channel with tens of thousands of cached messages later shows a
   real cost, this is the place to start — `renderedNodes` in `js/chat/messages.js` is already
   the right hook.
2. **The profile editor was not rebuilt** (section 3G's editor half: structured sections, live
   preview, validation, unsaved-changes indicator). The popout was fixed and the member list and
   chat work was prioritised ahead of it. Private notes remain private — nothing in this release
   touched that path.
3. **The accessibility pass is partial.** Focus rings, the reduced-motion block, the search
   field's labels and Escape handling, and `role="status"` on Discover loading are in. A full
   keyboard-trap, tab-order and contrast-ratio audit across every modal was not completed.
4. **Games / Moderation / Settings pages** got no visual pass beyond the Discover states.
5. **`Perf.report()` is not JSON-serializable** — `listeners()` returns a structure that survives
   `JSON.stringify` as `{}`. Reading individual fields works. Worth tidying; harmless.
6. **The build is unstamped** (section 6 above). It must be stamped before deployment.

## 9. Security

No rule was weakened, no read widened, no client-supplied user id trusted for a privileged
operation. `owners/` and `secretowner/` logic is untouched and still separate; nothing was added
that lets a browser grant site ownership. Moderation permissions remain enforced by the database
and API, not by hidden buttons. API identity is still resolved from the verified Firebase token.
No secret, webhook or service-account credential appears in any browser-delivered file — verified
by `test/security/no-secrets.js` (23 checks) and the rules audit (48 checks), both run against
this tree.
